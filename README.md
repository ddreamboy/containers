### Плохие практики в `Dockerfile.bad` и их исправление

1. Использование тега `latest` и тяжелого базового образа `FROM python:latest`
- Почему плохо: Тег `latest` непредсказуем, сборка может сломаться при обновлении образа. Полный образ `python` весит немало и содержит лишнии зависимости
- Исправление: В `Dockerfile.good` используется `python:3.12-slim`, конкретная версия для воспроизводимости и уменьшения размера контейнера

2. Копирование всего контекста перед установкой зависимостей `COPY . .` перед `pip install`
- Почему плохо: Любое изменение в коде приложения инвалидирует кэш слоя с зависимостями, заставляя Docker переустанавливать все пакеты заново при каждой сборке
- Исправление: Сначала копируем `requirements.txt`, устанавливаются зависимости, затем копируем код. Это позволяет использовать кэш Docker для зависимостей, если `requirements.txt` не менялся

3. Запуск от имени root по умолчанию
- Почему плохо: При несанкционированном доступе к приложению можно получить root-права внутри контейнера, что может облегчить побег из контейнера или атаку на хост
- Исправление: Создаем отдельного и запускаем приложение от его имени

4. Множество инструкций `RUN` = множество слоев
- Исправление: Разбиваем команды по логике в по инструкциям `RUN` с использованием `&&`

5. Установка лишних пакетов, например,`curl`
- Почему плохо: Увеличивает размер образа, тянет лишние зависимости
- Исправление: Не устанавливаем лишнего :)

### Плохие практики использования контейнера

1. Хранение данных внутри контейнера, например, логов. Убиваем контейнер - убиваем логи
2. Добавить помимо Python еще и Postgres с Redis в этот один контейнер, чтобы, например, хранить историю парсинга и кешировать последние 5 успешно обработанных ссылок. Сервис станет круче, но контейнер станет "толще" и нарушится принцип один сервис - один контейнер

### Когда НЕ стоит использовать контейнеры

1. Нативные приложения с графическим интерфейсом
2. Крупные монолитные приложения с зависимостью от железа

Запкус хорошего контейнера с монтированием volume
```bash
mkdir -p habr_adapter/logs

chmod 777 habr_adapter/logs

docker build -t habr-adapter-good -f habr_adapter/Dockerfile.good habr_adapter/

docker run -d -p 7000:7000 -v ./habr_adapter/logs:/app/logs --name habr-app habr-adapter-good
```

> если запустили хороший контейнер, остановите его перед запуском плохого
```
docker stop habr-app
```

Запкус плохого контейнера без монтирования volume
```bash
docker build -t habr-adapter-bad -f habr_adapter/Dockerfile.bad habr_adapter/

docker run -d -p 7000:7000 --name habr-no-app habr-adapter-bad
```
